验证环境：macOS、Clash Verge Rev 2.4.7、Mihomo 1.19.21、西安电子科技大学 `stu-xdwlan`。

结果：保留代理和 TUN，通过定向分流完成校园网认证。

## 1. 最后怎样解决了问题

保留系统代理和 TUN，只为校园认证网站增加一个专用直连出口，其他代理配置保持原样。

最终方案包含三部分：

1. `captive.apple.com` 保持直连，用于 Mac 的联网检测。
2. `w.xidian.edu.cn` 使用名为 `Campus-Auth-WiFi` 的专用直连出口，明确从本机 Wi-Fi 网卡 `en0` 发出连接。
3. 登录时使用这次校园网实际返回的入口 [https://w.xidian.edu.cn/index_8.html](https://w.xidian.edu.cn/index_8.html)。

另外，Clash Verge 在添加专用出口时，会把它加入普通代理组的候选列表。本次通过当前订阅的扩展脚本去掉了这项自动添加，让这个出口只被校园认证规则引用。

**成功的是这套组合方案。** 本次没有分别做“只更换入口”和“只绑定网卡”的独立实验，因此不能断言某一项是唯一根因，也不能保证只改其中一项就足够。

## 2. 原来的问题与约束

最初的现象是，连接校园 Wi-Fi 后，开启代理时认证页面不弹出；关闭代理后页面能出现，认证成功后才能正常上网。

目标是在保持代理运行的情况下完成校园网认证，处理时有明确约束：

- 不关闭代理或 TUN。
- 不改变其他流量的既有分流方式。
- 尽量只调整校园认证相关流量。

最初添加两个域名的普通直连规则后，问题没有完全解决。连接 `stu-xdwlan` 时，还出现了“设备不在认证范围内”的提示。

排查时需要在校园 Wi-Fi 下采集网络状态和认证响应。其他网络下的结果只能作为对照，不能替代校园网环境中的测试。

## 3. 为什么开启代理后，认证页面不自动弹出

**连接 Wi-Fi 与弹出认证窗口是两个步骤。** 电脑连上无线网络、拿到 IP 地址，只说明接入了网络，不代表已经获得外网访问权限。认证窗口通常依赖系统或浏览器的联网检测，并不是无线接入点直接在电脑上打开了浏览器。

### 3.1 正常情况下，系统怎样发现需要登录

macOS 会使用联网检测服务判断网络状态。Apple 将 `captive.apple.com` 列为用于认证网络联网验证的地址。[Apple 官方说明](https://support.apple.com/en-us/101555)

可以把正常流程简化为：

1. 电脑连接校园 Wi-Fi，获得 IP 地址、网关和 DNS。
2. 系统发出联网检测请求。
3. 未认证时，校园网络可能拦截 HTTP 检测请求，返回认证页面、重定向或包含跳转逻辑的网页。
4. 系统根据响应判断是否需要认证，并尝试显示登录窗口。
5. 用户完成认证后，校园网络放行相应的上网请求。

系统检测、弹窗展示和页面加载中，任意一步失败，都可能表现为“连上了 Wi-Fi，但没有弹出登录页面”。不同系统版本和校园网设备的具体行为也可能不同。

### 3.2 代理可能打断检测或页面加载

开启代理后，部分检测请求或认证页面请求可能被交给本地代理，再由代理决定如何连接目标。如果校园网尚未放行外网，而这类请求又需要先连接远端代理节点，就会形成依赖循环：

```text
访问认证页面需要先连上代理节点
连接代理节点又需要校园网先完成认证
```

此时，请求可能超时或失败。系统拿不到有效的认证引导内容，就未必能够弹出可用的登录窗口。Mozilla 的认证门户说明也指出，VPN 或代理可能妨碍访问认证页面，因为网络可能要求先登录，才能建立代理连接。[Mozilla 官方说明](https://support.mozilla.org/en-US/kb/captive-portal)

TUN 和 DNS 接管还会影响请求实际经过的路径。即使浏览器没有显式使用系统代理，流量仍可能进入 TUN；即使规则命中 `DIRECT`，连接也仍由 Clash 处理。因此，仅仅看到“直连”两个字，还不能判断认证服务能否通过正确的网卡访问。

这不表示开启代理一定会破坏认证，也不表示 fake-IP 必然导致弹窗失败。是否受影响，要看具体请求的规则、解析结果、出口和响应。

### 3.3 本案例能确认到哪一步

本案例中，开启代理时最初没有出现可用的认证窗口；添加普通直连规则后，认证入口访问仍存在失败。后续对照测试发现，绑定真实 Wi-Fi 网卡访问 HTTPS 可以获得响应，而经过当时的 Clash 代理路径会超时。

联网检测的响应中还包含校园认证入口的跳转表单。这说明校园网络能够返回认证引导，但并不能证明 macOS 的自动检测进程当时也成功收到了并处理了同一响应。诊断工具发出的请求与系统自己的检测请求，不能当作完全相同的一次访问。

因此，**本案例支持“代理相关的访问路径妨碍了认证流程”这一判断，但没有捕获最初系统检测进程的完整日志，不能把弹窗失败精确归结为单一内部原因。** 最终验证的是，在保持代理和 TUN 开启的情况下，可以通过指定入口完成认证；并未验证每次重新连接都一定恢复自动弹窗。

这也是为什么解决方案同时处理联网检测地址和认证网站，而不是只等待系统弹窗。

## 4. 为什么“代理开着”和“认证页面直连”可以同时成立

校园认证是本机与校园网认证服务之间的交互，可以单独走直连。其他请求仍按既有规则处理，不需要为了认证而关闭整个代理。

| 名称 | 在这次问题中的含义 |
| --- | --- |
| 系统代理 | 浏览器等应用可以把请求交给本机 Clash 端口，例如 `7890`，具体以客户端设置为准。 |
| TUN | Clash 创建的虚拟网卡，可接管系统流量。macOS 上常见名称为 `utun` 加数字，编号可能变化。 |
| `DIRECT` | Clash 直接连接目标服务器，不使用远端代理节点。它不等于请求完全绕过 Clash 或 TUN。 |
| fake-IP | Clash 为域名返回的虚拟地址，例如 `198.18.0.0/16` 范围内的地址。它不是校园网分配给电脑的真实地址。 |
| `en0` | 示例中的实际 Wi-Fi 网卡。应用配置前需要核对自己的网卡名称，不能直接照搬。 |

所以，把认证域名设为 `DIRECT` 是第一步，但不一定解决出口网卡选择、DNS 处理或认证入口不匹配的问题。

本次最终配置明确指定了认证请求的网卡：

```text
应用请求 → Clash 规则匹配
├─ w.xidian.edu.cn → Campus-Auth-WiFi → Wi-Fi 网卡 en0 → 校园认证服务器
├─ captive.apple.com → 原 DIRECT 直连
└─ 其他域名 → 按原有分流规则处理
```

这张图描述的是配置关系，不表示每个应用请求都经过完全相同的入站路径。

## 5. 排查得到的证据

### 5.1 校园 Wi-Fi 确实分配了地址

通过 Wi-Fi 网卡获得的校内地址、默认网关、DHCP 指定的 DNS，以及与其他网络的对照，确认诊断记录是在校园网环境中采集的。这些信息用于确认网络环境，具体设备地址不影响下文分析。

工具里的 Wi-Fi 名称查询仍显示“未关联 AirPort 网络”。这个输出与网卡地址、DHCP 信息以及实际访问响应不一致，所以没有把它当成“电脑没连 Wi-Fi”的依据。该条查询的具体失败原因未继续定位。

### 5.2 两条普通直连规则已生效，但还不够

最初增加的是：

```yaml
- DOMAIN,captive.apple.com,DIRECT
- DOMAIN,w.xidian.edu.cn,DIRECT
```

Clash 的运行中规则列表显示了这两项，日志也曾明确显示：

```text
dial DIRECT (match Domain/w.xidian.edu.cn)
```

因此，后续失败不能简单解释成“忘了加规则”或“规则没有保存”。

但当时访问认证入口仍出现 `502`、连接超时或连接关闭。普通 `DIRECT` 并没有让这台电脑完成认证。

### 5.3 HTTP 与 HTTPS 需要分别检查

认证网站可能通过 HTTP 引导跳转，再通过 HTTPS 展示登录页。只测试 HTTP，或者只看状态码而不检查页面中的跳转逻辑，容易漏掉关键线索。本案例的关键对比如下：

| 检查方式 | 当次结果 | 可以说明什么 |
| --- | --- | --- |
| 通过 Clash 端口访问 HTTP 认证入口 | `502 Bad Gateway` | 这条访问路径失败，不能据此认定认证服务器整体宕机。 |
| 通过 Clash 端口访问 HTTPS 认证入口 | 建立代理隧道后，TLS 连接超时 | 当时经过该路径没有获得 HTTPS 页面。 |
| 固定认证服务器 IP，并绑定 `en0` 访问 HTTPS | `302`，跳转到 `index_1.html` | 本机从真实 Wi-Fi 网卡可以访问该服务器的 HTTPS 服务。 |
| 访问 Mac 联网检测页面 | `200`，正文包含跳往 `index_8.html` 的表单 | 校园网络返回了认证引导内容。 |

成功的 HTTPS 探测同时固定了服务器 IP 和网卡，改变了两个条件。这个结果支持进一步检查真实网卡出口，但它本身不能证明“问题百分之百只在网卡选择”。

本次探测没有关闭证书验证，也没有通过忽略 TLS 错误来获得成功结果。

### 5.4 实际认证入口与网站默认入口不同

对认证网站根地址的成功 HTTPS 探测收到：

```http
HTTP/1.1 302 Moved Temporarily
Location: https://w.xidian.edu.cn/index_1.html
```

而校园网络对 Mac 联网检测请求返回的页面包含：

```html
<form name="CMCCWLANFORM"
      method="post"
      action="https://w.xidian.edu.cn/index_8.html"></form>
<script>
  CMCCWLANFORM.submit();
</script>
```

因此，本次校园连接实际被引向的是 `index_8.html`，不能只凭认证网站的域名相同，就认为网站默认入口一定适用于当前接入位置。

这给“设备不在认证范围内”提供了一个合理解释方向：认证入口可能没有对应当前的接入范围。但没有检查学校服务端的配置或错误码，**尚不能把这个解释写成已确认的唯一原因**。

表单名称中出现 `CMCC` 也不能单独证明用户必须选择中国移动套餐。本次只依据实际返回的认证地址处理，没有据此修改运营商选择。

### 5.5 DNS 与状态码需要谨慎解读

向 DHCP 指定的 DNS 发起查询时，记录里仍出现了 fake-IP 范围内的地址。当时 TUN 开启，配置包含 DNS 接管，所以这不能证明学校 DNS 本身返回了该虚拟地址。

还有两种容易误判的状态码：

- 联网检测的 `HTTP 200` 不等于已经能上网。本次返回的是认证跳转页面，而不是 Apple 正常的 `Success` 页面。
- HTTPS 代理请求中的 `200 Connection established` 是代理隧道建立响应，不等于目标认证页面加载成功。后续 TLS 仍可能超时。

## 6. 最终配置

本次把配置保存在当前订阅的增强配置中，没有直接修改生成出来的运行时配置文件。这样可以避免常规订阅更新直接覆盖手工添加的内容。

下面展示经过验证的配置形式。应用前先确认 Wi-Fi 网卡名称；如果已有自定义内容，应合并对应条目，不能整份覆盖。

**6.1 和 6.2 负责建立认证网站的访问路径；6.3 负责把专用出口限制在校园认证用途，不是打开页面的核心条件。** 三项配置保存生效后，还需要连接 `stu-xdwlan`，并访问本次验证的 `https://w.xidian.edu.cn/index_8.html`。本案例验证的是这套配置与正确入口的组合，不能理解成无论连接什么网络、使用哪个入口都能认证。

### 6.1 添加认证专用直连出口

在 Clash Verge 的 **订阅 → 右键当前订阅 → 编辑节点 → 高级** 中，添加：

```yaml
prepend:
  - name: Campus-Auth-WiFi
    type: direct
    ip-version: ipv4
    interface-name: en0
append: []
delete: []
```

各字段的作用是：

- `Campus-Auth-WiFi` 是规则引用的名称，不是新的远端代理服务器。
- `type: direct` 表示直接连接目标。
- `ip-version: ipv4` 让这个出口使用 IPv4，与本次已经验证的校园认证访问方式一致。
- `interface-name: en0` 明确绑定本机 Wi-Fi 网卡。

这里没有写死设备的校园网地址，也没有写死认证服务器的 IP。设备地址可以随 DHCP 分配变化，认证网站仍通过域名访问。固定服务器 IP 只用于排查时的对照探测。

### 6.2 只替换认证域名的规则目标

在 **订阅 → 右键当前订阅 → 编辑规则 → 高级** 中，当前配置为：

```yaml
prepend:
  - 'DOMAIN,captive.apple.com,DIRECT'
  - 'DOMAIN,w.xidian.edu.cn,Campus-Auth-WiFi'
append: []
delete: []
```

`DOMAIN` 匹配完整域名。对 `w.xidian.edu.cn` 而言，`index_8.html`、其他路径以及同域名请求都会命中这项规则，其他域名不会匹配它。

规则放在前面，是为了先于原订阅中的通用规则生效。没有把整个 `xidian.edu.cn`、全部私网地址或所有 Apple 服务一起改到这个出口。

### 6.3 防止专用直连出口进入普通代理组

添加节点后，检查生成的配置发现，Clash Verge 自动把 `Campus-Auth-WiFi` 加入了普通 `Proxy` 组的候选列表。

这次保存没有切换当前选中节点，但留下这个候选项会扩大它的可选范围。为符合“只供校园认证使用”的要求，在当前订阅的 **扩展脚本** 中增加了过滤：

```javascript
function main(config) {
  // Keep the campus-only direct outbound out of normal proxy selectors.
  for (const group of config["proxy-groups"] || []) {
    if (Array.isArray(group.proxies)) {
      group.proxies = group.proxies.filter(name => name !== "Campus-Auth-WiFi");
    }
  }
  return config;
}
```

这个脚本只移除代理组候选列表中的同名项，不删除专用出口本身。认证规则仍然可以直接引用它。

如果当前订阅的扩展脚本已有其他逻辑，应保留原逻辑并合并过滤部分，不要直接覆盖。

### 6.4 配置保存与订阅更新

通过当前订阅的 **编辑节点**、**编辑规则** 和 **扩展脚本** 保存上述内容，后续也优先从这些入口维护。不要直接编辑自动生成的运行时配置。

这些修改作用于当前订阅。切换其他订阅时，需要重新核对它是否带有相同配置。

## 7. 配置与认证结果怎样验证

本次验证分为三个层次。

**配置校验。** 修改前，使用本机安装的 Mihomo 对专用直连出口做了配置校验，结果通过。这只证明内核接受这种写法，不证明校园登录已经成功。

**应用前后比较。** 对生成配置进行结构比较，忽略 YAML 字段顺序变化后，最终只存在两项预期差异：增加专用直连出口，以及替换认证域名的一条规则目标。原代理组内容、其他规则、DNS 和 TUN 配置保持一致。Clash Verge 设置文件也与修改前一致。

**运行状态与实际使用。** Clash 的规则界面显示认证域名正在使用 `Campus-Auth-WiFi`，系统代理与 TUN 均保持开启。切回校园 Wi-Fi 后，通过指定入口完成了实际认证。

因此，这次验证同时确认了配置改动的范围，以及组合方案在本次校园连接中的实际效果。

## 8. 后续怎样使用

日常连接时，保持现有代理和 TUN 设置，连接 `stu-xdwlan`。如果没有自动出现认证页，新开标签页访问：

[https://w.xidian.edu.cn/index_8.html](https://w.xidian.edu.cn/index_8.html)

这份记录证明的是指定入口配合最终配置可以完成本次认证，并没有单独验证系统的自动弹窗在所有后续重连中都能恢复。

`index_8.html` 是本次校园网络实际返回的入口。将来学校调整认证系统、切换校区或使用其他 SSID 时，应以那次网络返回的入口为准，不要把它当成永久适用于所有场景的地址。

如果再次失败，先保留原有代理状态，并记录以下信息：

1. 当前连接的 SSID，以及完整报错文字。
2. 认证页的路径，特别是是否又进入了其他 `index_*.html` 或旧的带参数页面。
3. Clash 日志是否命中 `Campus-Auth-WiFi`。
4. 本机 Wi-Fi 网卡名称是否仍为 `en0`。

如需离线排查，可以在校园 Wi-Fi 下保存诊断结果，再切到其他网络查阅资料。对外分享时只保留必要的状态码、规则命中和跳转路径，删除账号、Cookie、订阅凭据、设备地址及个人文件路径。

## 9. 怎样撤回这次调整

需要恢复到“只有两个普通直连规则”的状态时，按依赖顺序撤回：

1. 在当前订阅的规则增强配置中，将 `DOMAIN,w.xidian.edu.cn,Campus-Auth-WiFi` 改回 `DOMAIN,w.xidian.edu.cn,DIRECT`，保存。
2. 在节点增强配置中移除 `Campus-Auth-WiFi` 条目，保留其他已有节点，保存。
