#### Question

##### 1. 为什么提高检索效率可以通过将文档切分成更小的块来实现？

将文档切分为更小的块（Chunks）能够提升检索效率与效果，核心原因主要体现在以下几个方面：

1. **避免语义稀释（聚焦单一语义）**
    - 向量嵌入模型（Embedding Model）通常将整段输入压缩为一个固定维度的向量。
    - 如果文档过长，会包含多个主题或细分子话题，向量表示会被“平均化”或稀释；
    - 切分为较小的块能确保**每个向量表达的语义更聚焦、更纯粹**，使 Query 向量与真正相关信息的余弦相似度匹配度更高。
2. **提高信噪比与生成阶段的上下文效率**
    - 检索到的结果最终需要喂给 LLM（如 Claude 或 GPT）作为 Prompt 的上下文。
    - 如果返回整篇长文档，其中大量无关内容会挤占模型的上下文窗口（Context Window），不仅增加 API 调用成本与推理延迟，还会造成“大海捞针”效应（Lost in the Middle），降低最终生成的准确性。
    - 小块只提供最关键的事实片段，大幅提升输入给 LLM 的**信噪比**。
3. **适配 Embedding 模型的输入长度限制**
    - 大多数向量模型都有固定的最大 Token 长度（如 512、2048 等），超出部分会被截断丢弃。
    - 切分小块可确保整篇文档的全部内容都能被完整编码入库，避免信息丢失。

> **需要注意的副作用（即本文提到的 Contextual Retrieval 解决的问题）：**块切得太小会导致**上下文孤立（Context Loss）**。例如一段代码或一句话可能只写着“`if status == 5: return false`”，缺乏“这段代码属于哪个模块/函数”的前提，导致检索时搜不到。因此文中提出的 **上下文嵌入（Contextual Embeddings）**，就是给切分后的小块前置一段由 LLM 总结的全文背景说明，既保留了小块的精准度，又补齐了全局语境。

#### BM25

**BM25（Best Matching 25）** 是一种在信息检索和搜索引擎中广泛使用的**基于概率统计的关键词匹配排序算法**，也是工业级全文搜索引擎（如 Elasticsearch、Lucene）的默认相关性评分算法。

##### 1. 核心机制与原理

BM25 可以看作是传统 **TF-IDF** 的进阶优化版，它计算一个查询（Query）和文档（Document）之间的相关性分数，主要引入了两个关键改进：

- **词频饱和度（Term Frequency Saturation）：**
    - 在传统 TF-IDF 中，某个词在文档中出现的次数越多，权重线性或无上限增长。
    - BM25 认为词频带来的增益是递减的（边际效益递减）。例如，一个词出现 20 次和出现 100 次，对文档主题的贡献差异并不大，BM25 会通过参数将其平滑限制在一个上限内。
- **文档长度归一化（Document Length Normalization）：**
    - 长文档因为字数多，天然更容易包含查询词。
    - BM25 会根据当前文档长度相对于语料库中“平均文档长度”的比值进行惩罚，防止长文档仅仅因为词多而占便宜。

##### 2. 在 RAG（混合搜索）中的作用与优势

在当前页面介绍的 RAG（检索增强生成）流程中，BM25 通常与**向量语义检索（Semantic Search）**互补，组成**混合搜索（Hybrid Search）**：

| **特性** | **向量语义检索 (Vector Embedding)** | **BM25 关键词检索** |
| --- | --- | --- |
| **擅长领域** | 理解语义、同义词、意图与模糊概念 | 精确匹配、专有名词、特定报错信息 |
| **代码/专业场景** | 容易漏掉生僻的变量名或完全匹配的短语 | **对函数名、类名、错误代码（如 `404`、`DiffExecutor`）极度精准** |
| **计算与成本** | 需要调用 Embedding 模型，计算复杂度较高 | 纯倒排索引查表计算，**速度极快且无模型调用费用** |

##### 3. 当前页面中的“上下文 BM25”技巧

在页面探讨的实现中，传统的 BM25 只能搜索切块后的**原始文本**。如果代码块里只有一段逻辑而没有类名/模块名，BM25 就会失效。

所谓 **上下文 BM25（Contextual BM25）**，就是让 BM25 同时建立索引并搜索：

\text{原始 Chunk 文本} + \text{LLM 补充的上下文背景说明}

这样不仅向量检索能识别语境，BM25 也能依靠背景说明中的关键词实现精准匹配，再通过 RRF（倒数排名融合）将两者的排序结果融合。

#### TF-IDF

TF-IDF即词频-逆文档频率，用来衡量词语在语料库中的重要程度。
TF词频衡量的是词t在文档d中的出现频率。
IDF逆文档频率衡量的是词语提供的信息量，即该词在所有文档中的出现频率或罕见程度。是包含该词语的文档数量与所有文档数量的对数倒数。
TF-IDF(t,d,D) = TF(t,d) × IDF(t,D)， TF-IDF数值较高代表词t在d中的出现频率较高而在整个语料库中的出现频率低。数值越高代表它的信息越重要，他是语料d的核心词或关键词，而数值越低表示它的信息越小，通常是常见词或者很少出现的词。

#### Mean Reciprocal Rank(MRR)平均倒数排名

**MRR（Mean Reciprocal Rank，平均倒数排名）**

- **定义与作用**：评估检索/排序系统质量的指标，衡量用户从首位开始浏览时，能多快看到第一个正确答案。
- **计算公式**：
\text{MRR} = \frac{1}{\vert{}Q\vert{}} \sum_{i=1}^{\vert{}Q\vert{}} \frac{1}{\text{rank}_i}
    - \vert{}Q\vert{} 为查询总数。
    - \text{rank}_i 为第 i 个 query **首次命中正确答案的排名位置**。
    - 若该 query 在设定的截断范围（k）内未命中任何正确答案，则该项记为 0。
- **取值范围与含义**：范围在 [0, 1] 之间。数值越接近 1，说明系统越倾向于将正确答案排在最前列；数值越大代表排序（Ranking）性能越好。

#### Claude Basic RAG

##### Background

选取了100个问题和相关的文档，k = 3

##### Metrics

1. Precision
2. Recall
3. F1 Score
4. MRR
5. End to End Accuracy: 使用LLM来对模型生成的最终回答和真实标准答案是否一致做出二分类(LLM-as-a-judge)

##### Level 1 Basic Rag

1. 根据子标题对整个文档进行切分chunk
2. 对每个chunk进行embedding
3. 对于每个问题通过向量余弦相似度计算出最相关的k个文档
4. 计算Performance(Metrics 1, 2, 3, 4)
5. 将问题和检索出来的文档作为上下文传给模型回答，使用LLM对回答是否正确做出评判(Metrics 5)

> 痛点：简单对子标题进行切分，可能会发生语义稀释，核心语义被大量的细节淹没，无法准确理解chunk观点chunk会丢失上下文信息，如果下一个子标题中使用或代指了其他子标题中的名词，无法理解其含义生成阶段在长篇大论中找答案容易收到注意力分散或迷失在中间的影响，漏掉真正关键的那句话**固定检索 Top-k 的硬截断瓶颈**：测试集中存在需要多跳推理（Multi-hop）的复杂问题（答案分散在 2\~3 个切片中）。由于纯向量匹配的精细度不够，正确切片容易被挤到第 4、5 位，固定截断 k=3 会直接导致漏召回（Recall 只有约 66%）

##### Level 2 Summary

在Level 1 的基础上引入摘要，事先通过LLM对每个子标题的内容进行总结，将两三句话的摘要拼接到语料后面，将子标题、正文和摘要一起作为chunk进行embedding，增强了核心主题在向量中的权重。

> 改进:提高了Recall， 说明摘要帮助了Embedding模型更好的理解整体内容，证明了Level 1 的语义稀释问题确实存在**显著提升了端到端准确率（71% \rightarrow 79%）**：将摘要一并作为 Context 传给生成模型，使 LLM 在面对冗长技术细节时能更直接地抓住核心事实，减少了误读和幻觉。

> 痛点:两三句话的摘要可能在概括长文本的时候出现问题，无法完全概括，并且会丢失细节**粗粒度语义匹配的精度瓶颈（Precision 依然只有 0.45 左右）**：单纯靠向量相似度无法细致区分相似概念（例如不同 API 的鉴权细节），召回池中仍有超过一半的切片是无关噪音。**召回率上限未被打破**：虽然加了摘要，但在面对多切片问题时，仍然受限于第一轮直接卡死 k=3 的截断机制，丢失了未进 Top-3 的正例文档。

##### Level 3 Re-Rank

在Level 2 的基础上引入Re-Rank：

1. 扩大预选索引范围，扩大到20个
2. 然后将这20个**切片的摘要与标题**（如果直接塞 20 个完整长切片，Prompt 会超长且极大增加重排成本与延迟）和问题一起给打分模型，进行Re-Rank，将这20个文档按照相关性进行排序
3. 选取最相关的k个chunk作为Context传给最终生成模型

> 改进：**MRR 大幅提升（0.77 \rightarrow 0.87）说明**：Claude 作为重排器具备强大的细粒度语义理解能力，能把真正最核心、最切题的文档精准推到第 1 名（排序质量质变）。**End to End Accuracy 达到最高（81%）说明**：LLM 生成回答对上下文的排序位置高度敏感（减少“迷失在中间”现象）。排在首位的高信息密度切片直接保障了生成答案的准确性与完整度。

> 痛点:固定选取k个答案，而文档可能的答案少于k个，导致Precision不高**增加了系统延迟（Latency）与 API 调用成本（Cost）**。每次检索都需要额外调用一次 Claude 对 20 个切片的摘要进行推理打分，无法像单纯向量库检索那样做到毫秒级极速响应。

##### Problem

###### 1. 检索与筛选阶段的遗留问题

- **多跳检索（Multi-hop Reasoning）未被真正解决**：
    - 系统依然是“单轮单次检索（Single-shot Retrieval）”。
    - 对于强依赖两段分散逻辑的问题（如“A 功能的参数限制”与“B 功能的计费规则”需要结合），如果这两个切片在向量空间里差异较大，一次 Query 很难把两者同时挤进 Top-20 候选池。
- **关键词/精准词条盲区（缺少混合检索）**：
    - 全流程完全依赖稠密向量（Dense Vector，Voyage-2），缺乏传统的稀疏检索（BM25 / Keyword Search）。
    - 面对冷门 API 函数名、特定错误码（如 `529`、`overloaded_error`）或 IPv6 地址等专有名词时，纯向量检索容易出现“幻觉语义匹配”而漏掉字面精准匹配。
- **粗暴的“固定 Top-k 截断”限制**：
    - 重排后依然死板地截断取前 k=3 个。当问题只需要 1 个文档时会引入 2 个干扰项；当需要 4 个文档时又会丢失关键信息。系统缺乏根据重排置信度动态决定截断数量（Dynamic K / Threshold-based filtering）的机制。

###### 2. 生成与交互阶段的遗留问题

- **缺乏“拒答机制”（No Fallback / I don't know）**：
    - 系统 Prompt 设定了“尽可能依赖上下文”，但缺乏显式的拒答校验。如果检索阶段彻底未命中，模型在面对用户提问时依然有强行根据有限片段脑补、产生幻觉的风险。
- **缺乏可追溯的引用归因（Citations / Attribution）**：
    - 虽然向模型输入了切片，但最终输出给用户的是纯文本答案，没有强制要求模型输出“每个观点的依据切片与链接（Inline Citations）”，用户无法快速校验事实来源。

###### 3. 工程与成本架构层面的妥协

- **显著的响应延迟（High Latency）**：
    - Level 3 的每轮检索需要先调用一次 LLM 阅读 20 个切片的摘要进行重排，再调用一次 LLM 生成答案。两次串行的模型推理使得端到端响应时间大幅增加，难以直接用于高并发或毫秒级交互场景。
- **API 与 Token 成本倍增**：
    - 重排步骤将 20 个切片的摘要全部灌入 Prompt，无论用户问的问题有多简单，都消耗了固定的大模型 Context 开销。
- **数据离线构建成本高昂（Cold Start / Maintenance）**：
    - Level 2 为每个切片预先生成高质量摘要，如果企业知识库有数万甚至数百万切片，预先为所有切片调用 LLM 生成摘要并入库的计算与金钱成本极高；且一旦原始文档频繁修改，维护摘要增量更新的代价很大。

##### Conclusion

1. 纯向量检索只能判断语义相似度，属于全局模糊匹配，无法理解细节并站在语义层面回答问题。因此检索出来的东西可能只是相关、字面重合度高，但实际上无关，导致没有精准地回答问题(参考我在英语听力)

##### **优化一：上下文嵌入（Contextual Embeddings）**

**解决痛点**：单块切分导致的孤立语义缺失。

**做法**：在入库预处理时，将“全文”与“当前 chunk”一起交给 Claude，借助 Prompt Caching 生成 50–100 token 的全局定位描述并拼接到文本中再做向量化。

**代价与收益**：带来最大的单项准确率跃升（Pass@10 从约 87% 提至 92%），且属于一次性建库成本，不增加后续每次查询的延迟。

##### **优化二：混合检索（Contextual BM25 Hybrid Search）**

> **解决痛点**：纯向量检索容易漏掉生僻关键词、专用变量名或函数名。

> **代价与收益**：提升专有名词匹配精度，但需要额外维护 Elasticsearch 或具备全文检索能力的检索组件。

**做法**：引入 BM25 关键词检索，并将生成的上下文一同编入 Elasticsearch 倒排索引，最后通过倒数排名融合（RRF）加权合并稠密向量与稀疏关键词结果。

###### 第一步：双路独立并行检索（各取 Top-150）

当用户发起一个查询（Query）时，系统会**同时走两条完全独立的检索路径**：

1. **第一路：上下文向量检索（Dense Retrieval）**
    - 调用 Voyage AI 将用户的 Query 转为向量。
    - 在存储了“上下文 + 原始 chunk”向量的向量库中计算余弦相似度。
    - 取出语义最接近的前 **150** 个候选块。
2. **第二路：上下文 BM25 检索（Sparse Retrieval）**
    - 直接把用户的 Query 字符串发给 Elasticsearch。
    - Elasticsearch 同时在两个文本字段中做关键词词频匹配：`content`（原始 chunk）和 `contextualized_content`（Claude 生成的上下文）。
    - 取出关键词匹配得分最高的前 **150** 个候选块。

###### 第二步：倒数排名融合（RRF，加权合并）

由于向量检索给出的是“余弦相似度”（通常在 0 到 1 之间），而 BM25 给出的是“关键词相关性打分”（分值范围不固定，可能几十上百），**两者的绝对分数无法直接相加**。

代码中使用了基于排名的**倒数排名融合（Reciprocal Rank Fusion, RRF）**：

- 如果某个块在向量检索中排第 r_{\text{semantic}} 位，它的向量贡献分为：
\text{score}_{\text{semantic}} = 0.8 \times \frac{1}{r_{\text{semantic}} + 1}
- 如果该块同时也在 BM25 检索中排第 r_{\text{bm25}} 位，它的 BM25 贡献分为：
\text{score}_{\text{bm25}} = 0.2 \times \frac{1}{r_{\text{bm25}} + 1}
- **最终综合得分** = 向量贡献分 + BM25 贡献分。

如果一个块在两边都名列前茅，它的综合得分就会极高；即便它只在某一边排在前面，也能获得一定的保底分数。

###### 第三步：按综合得分重排，取最终 Top-k

系统根据上面计算出的综合得分降序排序，最终选出前 k 个（如 Top-5、Top-10 或 Top-20）作为检索结果交付给后续流程。

##### **优化三：重排序（Reranking）**

**解决痛点**：初筛阶段仅凭单向量点积或简单词频无法深入理解复杂语义相关性。

1. 向量检索采用双塔模型，会把Query和Document都压缩到一个高维向量上，最终计算两者的余弦相似度。信息压缩会导致关键信息的缺失，只能判断两个文本在宏观概念上是否属于同一个主题；
2. 简单词频又只衡量字面的出现频率和稀缺度来判断重要程度，无法区别关键词出现的语境。

**做法**：第一阶段大范围召回更多候选块（例如取 Top-100），第二阶段使用 Cross-Encoder 架构的重排序模型（如 Cohere Rerank）对候选块进行深度打分精排。

> 这里一般不使用通用大模型来进行打分（成本与延迟太高），而是使用专用的Reranker。他们会直接把Query与Chunk拼在一起一次性喂给Encoder，然后注意力机制在每个词之间进行完全的交叉比对，模型能精准感知到上下文约束、主谓宾逻辑、条件判断与修饰关系。输出不生成任何文字，而是通过最后一层的分类头输出一个浮点数作为相关性打分，

**代价与收益**：检索失败率降至最低（Pass@10 达到约 95.3%），但会直接给每次用户查询引入约 100–200 毫秒的延迟与额外的单次 API 成本。

### 现代 RAG 演进技术与方案整理

#### 1. 本地开源 Reranker（替代闭源商业 API）

- **核心思路**：使用本地/私有 GPU 部署开源 Cross-Encoder 模型（如 BAAI 的 `bge-reranker-large`、`bge-reranker-v2-m3`），替代 Cohere 等外部商业 API。
- **解决痛点**：消除外部 API 的网络 RTT 延迟（从 100–200 ms 压缩至 10–30 ms 内网/本地推理）以及高频查询带来的单次调用账单成本。
- **典型工具/库**：`FlagEmbedding` (BAAI)、Hugging Face `transformers`。

#### 2. 父子分块 / 分层检索（Parent-Child / Hierarchical Chunking）

- **核心思路**：“小块召回，大块返回（Small-to-Big）”。
    - **索引阶段**：文本切分成极小粒度（如 100–200 tokens）生成向量，专注语义高密度匹配。
    - **生成阶段**：小块命中后，通过元数据反查并把所属的完整父级段落（如整节、整函数或整个类）传递给 LLM。
- **解决痛点**：避免了给每个切片额外生成几百字摘要/上下文的入库复杂度与截断风险，同时平衡了“高检索精度”与“大生成上下文”。
- **典型实现**：
    - LangChain：`ParentDocumentRetriever`
    - LlamaIndex：`HierarchicalNodeParser` + `AutoMergingRetriever`

#### 3. Agentic RAG / 自适应检索（智能体工作流）

- **核心思路**：将传统的“单向、被动、一次性”检索升级为具备自省能力的动态循环闭环。
    - **查询重写与拆解（Query Rewriting）**：遇到复杂或模糊问题，先由轻量模型改写或拆解成多个子查询。
    - **自省与评估（Self-Reflection / Grader）**：检索出候选块后，先打分校验内容是否足够回答该问题。
    - **动态兜底（Fallback & Fall-forward）**：信息不足时自动触发第二轮检索，或回退调用网络搜索。
- **解决痛点**：解决一次性检索失败导致答案彻底幻觉的问题，适应多跳逻辑推演和复杂长尾提问。
- **代表架构/论文**：Self-RAG (ICLR 2024)、Corrective RAG (CRAG)、LangGraph 自适应 RAG 模板。

#### 4. GraphRAG（知识图谱增强检索）

- **核心思路**：在入库时提取文档实体、关系与社区摘要（Community Summaries），构建结构化知识图谱。检索时结合拓扑路径做多跳遍历与全局聚合。
- **解决痛点**：纯向量与 BM25 擅长局部匹配，但极难处理**跨文档、全局总结性提问**（如“整个代码库中所有涉及状态流转的模块有哪些协同机制”）。
- **代表实现**：Microsoft `graphrag`。

#### 5. 长上下文直喂 + 服务端缓存（Long-Context Direct Feeding）

- **核心思路**：针对中小型知识库（几万至数十万 tokens，如单个微服务代码库、特定产品手册），省去切块与检索，直接将全部文档喂入百万级 Context 窗口（如 Claude / Gemini），并利用服务端的 Prompt Caching 降低后续交互成本。
- **解决痛点**：彻底摆脱分块边界割裂、召回漏检与上下文丢失的工程妥协。
